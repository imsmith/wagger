# Apache httpd (mod_security2) Generator — Design

Date: 2026-06-09
Status: Approved, pending implementation plan

## Problem

Wagger emits ModSecurity `SecRule` directives today via the Coraza generator,
but that output is a *standalone* `.conf` aimed at the Coraza engine. Operators
deploying on Apache need the same route-allowlist rules packaged for Apache's
`mod_security2` module: an `<IfModule>` guard, audit-logging directives, and
working-dir directives, in a drop-in include file.

The `SecRule` rule bodies are byte-for-byte identical between Coraza and
mod_security2. Only the surrounding packaging differs.

## Goals

- New `apache` provider producing a mod_security2-ready `.conf` include file.
- Reuse the existing SecRule rule-building/rendering logic — no duplicated rule
  logic between Coraza and Apache.
- Coraza output remains byte-for-byte unchanged after the refactor.

## Non-Goals (YAGNI)

- Bundling the OWASP Core Rule Set.
- Emitting a `LoadModule` line (managed separately via `a2enmod`).
- Wrapping rules in `<VirtualHost>` or `<Location>` (operator decides scope).
- Native request-rate limiting (mod_security2 has none; keep rate limits as
  comment annotations, same as Coraza).
- A separate downloadable-filename scheme.

## Architecture — shared SecRule core

Extract the logic Coraza and Apache share into a new pure-function module, then
build both providers on top of it.

### `Wagger.Generator.SecRule` (new)

Pure functions, no behaviour:

- `build_rules(routes, config)` → `{rules, catch_all_id}` — the rule-id
  sequence, `path-pattern`, `methods`, and rate-limit comment. Extracted
  verbatim from Coraza's `map_routes`.
- `render_rules(rules)` → the chained `SecRule` text blocks. Extracted from
  Coraza's `render_rule`.
- `render_catch_all(id, phase, status)` → the final deny rule.
- Shared helpers: `normalize/1`, `original_path_from_pattern/1`,
  `iso8601_now/0`, `parse_int/3`.

### `Wagger.Generator.Coraza` (refactored)

Same `Wagger.Generator` behaviour. `map_routes/2` and `serialize/2` now delegate
rule construction and rendering to `SecRule`. **Output must stay byte-for-byte
identical** — the existing `coraza_test.exs` is the regression guard.

### `Wagger.Generator.Apache` (new)

Implements the `Wagger.Generator` behaviour:

- `yang_module/0` → reads `yang/wagger-apache.yang`.
- `map_routes/2` → builds the `apache-config` instance tree: the shared rule
  subtree (via `SecRule.build_rules/2`) plus packaging leaves.
- `serialize/2` → wraps the rendered rules in mod_security2 packaging.

## Output shape — bare include file

Self-contained `.conf`, meant to be pulled in via `Include` or dropped into an
existing vhost. Everything inside an `<IfModule security2_module>` guard so it
no-ops when the module isn't loaded.

```apache
# Generated by Wagger for app: <prefix>
# Timestamp: <iso8601>

<IfModule security2_module>
  SecRuleEngine On
  SecRequestBodyAccess On
  SecDefaultAction "phase:1,log,auditlog,deny,status:403"

  # --- audit logging ---
  SecAuditEngine RelevantOnly
  SecAuditLog <audit_log_path>
  SecAuditLogParts ABIJDEFHZ

  # --- working dirs ---
  SecTmpDir <tmp_dir>
  SecDataDir <data_dir>

  # --- route allowlist (shared SecRule core) ---
  # GET /foo
  SecRule REQUEST_URI "@rx ^/foo$" "id:100001,phase:1,chain,allow"
    SecRule REQUEST_METHOD "@pm GET" "t:none"
  ...

  # Deny all undeclared paths
  SecRule REQUEST_URI "@rx .*" "id:190001,phase:1,deny,status:403,msg:'No matching route'"
</IfModule>
```

Engine directives + SecRules come from the shared core; audit-logging and
working-dir directives are Apache-specific. No `LoadModule` line.

## YANG schema — `yang/wagger-apache.yang`

Self-contained (no imports — the validator resolves each module against an empty
registry, matching how `wagger-coraza.yang` inlines everything). Container
`apache-config` mirrors the Coraza rule shape:

- `config-name`, `generated-at`, `rule-engine`, `default-action-phase`,
  `default-action-status`, `start-rule-id`, `rules` list, `catch-all-rule-id`

plus packaging leaves:

- `audit-log-path`, `tmp-dir`, `data-dir`

The `rules` list is duplicated in YANG (schemas are self-contained); only the
Elixir rule-building logic is shared via `SecRule`.

## Registration & config fields

`"apache"` joins the **Ingress Configs** group everywhere providers are listed:

- `lib/wagger_web/live/app_detail_live.ex` — `@providers` list, Ingress group,
  `@provider_modules` map, `@provider_config_fields` map
- `lib/wagger_web/live/hub_detail_live.ex` — `@providers` list, Ingress group,
  module map, config-fields map
- `lib/wagger_web/live/dashboard_live.ex` — `@providers` list
- `lib/wagger_web/controllers/generate_controller.ex` — `@providers` module map

Config fields for `apache`:

```text
prefix          Name prefix
start_rule_id   Starting rule ID (default 100001)
audit_log_path  Audit log path (default /var/log/apache2/modsec_audit.log)
tmp_dir         SecTmpDir (default /tmp)
data_dir        SecDataDir (default /var/cache/modsecurity)
```

All optional dirs/paths have defaults so a bare-prefix generate still produces a
loadable config.

## Testing

- `test/wagger/generator/apache_test.exs` (new) — mirrors `coraza_test.exs`:
  asserts the `<IfModule>` guard wraps everything; engine/audit/tmp-dir
  directives present; per-route chained SecRules with correct ids/methods;
  catch-all deny; rate-limit comments; and that the instance validates against
  `wagger-apache.yang`.
- `test/wagger/generator/coraza_test.exs` (unchanged) — regression guard proving
  the `SecRule`-core extraction left Coraza output byte-identical.
- Full suite (currently 648/648) to confirm no registration/snapshot
  regressions.
